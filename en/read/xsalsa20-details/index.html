XSalsa20 Stream Cipher

Article review and catalog-metadata acceptance are recorded separately. The library remains under construction.

Principles

Algorithm: XSalsa20 (XSalsa20 流密码). ### Salsa20’s 512-bit state

Salsa20 arranges a 256-bit key, a 64-bit nonce, a 64-bit block counter and 128 bits of constants into sixteen 32-bit words in a 4×4 matrix. Twenty ARX rounds (32-bit addition, rotation and XOR) are followed by adding the input back, producing a 64-byte keystream block. There are no S-boxes or secret-index table lookups. ### XSalsa20 derives a subkey first

XSalsa20 extends the nonce to 192 bits. It first runs HSalsa20 with the key and the first 128 nonce bits. HSalsa20 shares the 20-round core but omits the final input addition and selects eight words to form a 256-bit subkey; standard Salsa20/20 then uses that subkey, the remaining 64 nonce bits and a 64-bit block counter to generate the stream. ### Why the longer nonce matters

With a 64-bit nonce, random nonces under one key collide around 2^32 messages; a 192-bit nonce pushes that risk to about 2^96 messages. For protocols that choose a fresh random nonce per message, this is simpler than maintaining a global counter.

Why it matters

XSalsa20 is about nonce management, not a new round function. NaCl crypto_box uses X25519 for key agreement, XSalsa20 for encryption and Poly1305 for authentication; each message can carry an independent random 192-bit nonce without a cross-session counter.

It keeps Salsa20’s speed and ARX side-channel behavior, adding only one HSalsa20 subkey derivation whose cost is below one Salsa20 output block. The SKEW 2011 paper proves that a fast attack on XSalsa20 converts into an attack on Salsa20, so its security reduces to Salsa20.

Applications

libsodium exposes XSalsa20/20 as crypto_stream and crypto_stream_xor; NaCl crypto_box combines XSalsa20 with Poly1305; many language bindings and message-encryption libraries follow that combination.

It fits protocols that want long random nonces and high software speed. It is not a TLS cipher suite; TLS 1.3 uses ChaCha20-Poly1305 or AES-GCM, while XSalsa20 lives mainly in the NaCl ecosystem and custom protocols.

Limits & attacks

XSalsa20 provides confidentiality only, not integrity; it must be paired with Poly1305 or a higher-level AEAD. The nonce must still be unique: reusing the same key/nonce reproduces the same keystream, and ciphertext XOR reveals plaintext XOR.

A 192-bit nonce lowers the collision probability to an acceptable level; it does not permit reuse. The 64-bit block counter bounds one key/nonce pair to about 2^64 blocks of 64 bytes; after that the counter wraps and the key or nonce must change.

ARX software resists timing attacks, but hardware power and electromagnetic analysis can still recover state; HSalsa20 is not a general KDF, and the same key should not be reused across unrelated purposes.

History

Bernstein designed Salsa20 in 2005, and Salsa20/12 entered the eSTREAM software portfolio. In 2008 he proposed XSalsa20, extending the nonce to 192 bits with a security reduction; NaCl then combined XSalsa20 with Poly1305 in crypto_box, and libsodium continued the construction. It is a key node in ARX stream ciphers and in random-nonce design.
