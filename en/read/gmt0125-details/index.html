GM/T 0125 Chinese JOSE

Article review and catalog-metadata acceptance are recorded separately. The library remains under construction.

PrinciplesWhy it mattersApplicationsLimits & attacksHistoryWorked example & verificationReferences

Principles

Standard: Chinese JSON Object Signing and Encryption (国密 JSON Web 语法). GM/T 0125.2—2022 JWS has a JOSE header, payload and signature. The protected header is UTF-8 then base64url: (protected_b64=base64url(UTF8(header))); the payload is (payload_b64=base64url(payload)). The signing input is (M=ASCII(protected_b64|\text{“.”}|payload_b64)). (SGD_SM3_SM2) signs (M) with an SM2 private key, hashes with SM3 and encodes the signature in DER; (SGD_SM3_HMAC) computes (HMAC\text{-}SM3(K,M)) with 256-bit output. Compact serialization is (protected_b64|\text{“.”}|payload_b64|\text{“.”}|base64url(sig)); JSON serialization supports multiple signatures, but the union of protected and unprotected headers must have a required (alg) and unique names.

Why it matters

Chinese JOSE is not just “JWT with a different signature algorithm”. It treats (alg) as the algorithm identifier, (kid/jwk/x5c/x5t#sm3) as key identifiers, and separates protected from unprotected headers; a verifier that reads only the (alg) string without checking the key type repeats JWS algorithm confusion. The formula-level split is threefold: signing input is protected_b64 dot payload_b64; SM2 output is DER; HMAC output is 256 bits; verification requires (alg\in Allow(key)) and (key=KeyStore[Id]).

Applications

To generate, choose the algorithm first: (SGD_SM3_SM2) for SM2 signatures or (SGD_SM3_HMAC) for a shared-key MAC; build and encode the protected header, form (M), compute the signature and base64url it. To verify, parse compact or JSON serialization, check that (alg) exists and is allowed for the key, locate the key by (kid/jwk/x5c/x5t#sm3), rebuild (M) and verify. In multi-signature cases verify each signature; unprotected headers may carry presentation data but must not be the sole basis for a security decision.

Limits & attacks

There are four boundaries. First, unprotected headers are outside the signature and can be changed; any header that affects a security decision belongs in the protected header. Second, (alg) and key type must bind: treating an SM2 public key as an HMAC key or accepting (none) breaks verification. Third, base64url must omit padding and decode by the standard, and duplicate header parameters in JSON serialization must be rejected. Fourth, SM2 signatures are DER-encoded and not a fixed 64 bytes; implementations must not slice DER as a fixed-length value. The standard does not define JWT claim semantics, key lifecycle or side-channel protection.

History

GM/T 0125 “JSON Web cryptographic application syntax specification” was published on 2022-11-20 and took effect on 2023-06-01, in four parts: algorithm identifiers, signatures, data encryption and keys. Part 2 specifies JWS, with (SGD_SM3_SM2) and (SGD_SM3_HMAC) generation/verification and compact/JSON examples. The account follows the State Cryptography Administration announcement and Part 2, and does not mix generic JWT ecosystem algorithms into the Chinese identifiers.
